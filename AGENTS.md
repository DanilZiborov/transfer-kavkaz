# Инструкции для Codex — Transfer Kavkaz

## 1. Назначение и источник требований

Это репозиторий сайта индивидуальных трансферов по Северному Кавказу. Разработка ведётся итерациями: сначала полностью работоспособный MVP с демонстрационным контентом, затем визуальная доработка и подготовка к коммерческому запуску.

**Перед началом каждой существенной задачи прочитай `docs/TZ.md`.** Это утверждённый источник функциональных, визуальных и нефункциональных требований. Этот файл описывает способ работы, а не заменяет ТЗ.

Если задача, ТЗ и существующий код противоречат друг другу, укажи противоречие; не принимай самостоятельно новое продуктовое решение. Не изменяй `docs/TZ.md` и `AGENTS.md` без явного запроса.

## 2. Технологический стек

- Astro 7, статическая генерация страниц (SSG).
- TypeScript в строгом режиме.
- Нативный CSS, CSS-переменные и стили компонентов Astro.
- Нативный JavaScript / TypeScript для интерактивности.
- Astro Content Collections + Zod для типизированных данных направлений.
- GitHub Pages и GitHub Actions для сборки и публикации.

**Не добавляй без согласования:** React, клиентский роутер, CMS, серверное API, базу данных, UI-фреймворки и тяжёлые библиотеки анимаций. Выбирай простое решение с минимальным числом зависимостей. Не добавляй функциональность «на будущее», если её нет в ТЗ или текущей задаче.

## 3. Архитектура и код

- Разделяй страницы, переиспользуемые компоненты, данные и стили.
- Применяй один общий шаблон для страниц направлений, а не копируй страницы под каждое направление или пару городов.
- Контент, цены, контакты, галерею и отзывы храни централизованно, без дублирования в компонентах.
- Соблюдай строгую типизацию; не используй `any` без обоснования. Для импортов типов применяй `import type`, где это уместно.
- Используй семантический HTML, стандартные ссылки и кнопки. Не реализуй средствами JS то, что надёжно работает на HTML/CSS.
- Учитывай `base` GitHub Pages во внутренних ссылках и путях ресурсов. Не предполагай, что сайт всегда размещён в корне домена.
- Не придумывай реальные контактные данные, отзывы, достижения перевозчика или характеристики автомобиля. Демонстрационные данные явно обозначай как демо; ссылки не должны вести к случайным людям.

## 4. Дизайн и пользовательский опыт

- Ориентир: современный минимализм с тёплой атмосферой Кавказа, не буквальное копирование изображения-референса.
- Простая вертикальная композиция, крупный читаемый текст, много воздуха. Избегай перегруженных и сложных многоколоночных макетов.
- Главный баннер широкий, но не полноэкранный: горы, дорога, автомобиль и ясный призыв связаться.
- Приоритет — понятная навигация и доступность кнопок связи. Следуй требованиям ТЗ к sticky-шапке, якорям, мобильной контактной панели и CTA.
- Добавляй умеренные hover-эффекты и лёгкие анимации без тяжёлых зависимостей. Уважай `prefers-reduced-motion`.
- Не жертвуй читаемостью и производительностью ради эффектов.

## 5. SEO, доступность и производительность

- Генерируй готовый HTML для главной, каталога и страниц направлений.
- Соблюдай требования ТЗ к `title`, `description`, canonical, Open Graph, sitemap, robots и семантической структуре.
- Пока сайт содержит фиктивные данные, используй явно настраиваемый режим прототипа, исключающий его индексацию. Он должен отключаться при коммерческом запуске; не считай `robots.txt` единственным способом запретить индексацию.
- Оптимизируй изображения: адаптивные размеры, современные форматы, ленивую загрузку ниже первого экрана; главный баннер загружай приоритетно.
- Mobile-first, ширина от 320 CSS px, без горизонтальной прокрутки.
- Обеспечивай доступность с клавиатуры, видимый фокус, alt-тексты, адекватный контраст и корректное управление модальными элементами.
- Целевые показатели Lighthouse для мобильной версии: Performance ≥ 90, Accessibility ≥ 90, SEO ≥ 95 (учитывай, что режим `noindex` прототипа влияет на оценку SEO).

## 6. Как выполнять задачи

1. Прочитай текущую задачу, применимые инструкции и соответствующие разделы `docs/TZ.md`; сначала изучи существующий код.
2. Для крупных изменений кратко опиши план. Не переусложняй архитектуру и не переписывай несвязанные части проекта.
3. Выполни задачу минимальным понятным набором изменений. При разработке придерживайся уже существующих соглашений репозитория.
4. Проверяй типы и production-сборку. После появления соответствующих npm-скриптов используй `npm run check` и `npm run build`; если скрипт отсутствует или проверка невозможна, честно сообщи об этом. Не утверждай, что тест пройден, если не запускал его.
5. По возможности проверь поведение навигации, адаптивность, работу клавиатуры и прямые URL страниц.
6. В итоговом отчёте кратко перечисли изменения, выполненные проверки и оставшиеся ограничения.

Не меняй инфраструктуру, зависимости или архитектурные решения за пределами согласованной задачи. Не публикуй прототип как коммерчески готовый сайт, не подключай аналитику и сторонние сервисы без запроса. Для существенных изменений предпочитай отдельную ветку и Pull Request; не выполняй деплой или другие внешние действия без разрешения, выраженного в текущей задаче.
